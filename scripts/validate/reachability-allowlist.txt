# PR #5 — complete task board membership lifecycle: FULLY MOUNTED, nothing to list.
# BLOCKED ON AN ADAPTER THAT DOES NOT EXIST. Every service here is a pure reducer over a
# TaskBoardRepository whose `transaction` must be atomic, plus a TaskBoardCredentialIssuer that mints
# and hashes board capabilities, plus a TaskBoardSessionDirectory. There is no src/adapters/task-boards
# at all, so mounting this means PORTING the persistence and the credential minting — not wiring —
# and a capability store built by guesswork is a security boundary built by guesswork.
#
# RE-CHECKED by the second wiring unit, and the blocker is narrower and harder than "no adapter": the
# repository IS a snapshot the file-store pattern here already fits, but every grant in it is keyed on
# a `sessionCapabilityHash` — "hash of the daemon-owned session credential" — and no such credential
# exists anywhere in this daemon. `sessionCapabilityHash` appears in no file outside this directory: a
# session authenticates with the shared admin token plus the `x-ferretry-session-id` header, which is
# an ATTRIBUTION, not a secret only that session holds. Mounting boards therefore means first minting
# a per-session credential at session start — which is not mounted — and every grant, invitation proof
# and child grant hangs off it. That is the security boundary, and it cannot be invented here.
#
# RE-CHECKED by the fourth wiring unit now that session start IS mounted, and the blocker moved rather
# than fell: minting the credential is no longer the binding constraint, DELIVERING it is. The CLI
# reads it from the environment and the launch path cannot set one — see "THERE IS NO WAY TO HAND A
# SESSION A SECRET" in the header above. Until that seam exists, every peer-scoped board command in
# `fy task-board` refuses before it sends, so the whole surface would be operator-only.
#
# THAT SEAM NOW EXISTS, and the "no way to hand a session a secret" blocker above is SPENT — read it
# as history rather than as the current state. `TmuxLaunch` carries an `env`, `newSessionArguments`
# emits `-e NAME=VALUE` before the command word, `TmuxSessionLifecycleLauncher` reads the session's
# environment at every launch, and `SessionLifecycleService.create` mints a 256-bit credential for
# EVERY session: the SHA-256 goes on the record as `sessionCapabilityHash` — which is the exact field
# every grant, invitation proof and child grant here is keyed on — and the plaintext goes to one 0600
# file in the session's directory, delivered to the pane as `FY_SESSION_BOARD_CAPABILITY`. It is
# deliberately absent from the session document, because that document is projected by the API.
#
# WHAT IS ACTUALLY LEFT IS A PORT OF FOUR ADAPTERS AND ONE UNDECIDED SECURITY QUESTION. The four are
# mechanical and the port interfaces in `types.ts` specify them completely: `TaskBoardRepository`
# (a snapshot with an atomic `transaction` — the `FileTaskStore` + `KeyedSerialExecutor` pattern in
# `adapters/tasks` already fits it), `TaskBoardCredentialIssuer` (`id`, `capability`, `hash` — the
# same shape as `NodeSessionCredentialIssuer`), `TaskBoardClock`, and a `TaskBoardSessionDirectory`
# over the session index, which can now answer `sessionCapabilityHash` for every session. The route
# surface is fully known too: `packages/cli/src/adapters/tasks/fy-task-board-gateway.ts` names all
# eleven paths under `/v1/task-boards`.
#
# THE UNDECIDED QUESTION, and the reason this unit stopped rather than mounting: `fy task-board
# create`, `mark-done`, `coordinator-replace` and `revoke` authenticate with
# `FY_BOARD_ADMIN_CAPABILITY` — the OPERATOR's capability, which `board-credentials.ts` documents as
# "deliberately unavailable inside a teammate pane". Nothing in this daemon mints that secret, and
# nothing gives a human a way to read it: it is not the admin API token, and there is no operator
# credential file, no `fy` command that prints one, and no design anywhere in the repo for how it
# reaches the person typing the command. Inventing that distribution mechanism is inventing a
# security boundary, so it wants a deliberate decision rather than a wiring unit's guess — and
# without it `create` cannot be called at all, which means no board can come into existence for any
# of the other ten routes to address.
# THE UNDECIDED QUESTION WAS ANSWERED BY THIS REPOSITORY, NOT BY A GUESS, AND THE BOARD IS MOUNTED.
# `src/lib/runtime/mounts/task-boards.ts` serves EIGHT of the CLI's eleven board routes over the
# reducers listed here, and the four adapters `types.ts` specified are ported in
# `src/adapters/task-boards/`: a file repository whose one document makes `transaction` genuinely
# atomic, a credential issuer, a session directory over the session index, and the operator's
# capability.
#
# The blocker recorded above was "nothing mints `FY_BOARD_ADMIN_CAPABILITY` and no design says how it
# reaches the person typing the command". This daemon had already made that exact decision for that
# exact principal: `StateApiCredentials` mints the human's API token into `<state home>/api-token` at
# 0600 on first boot and the operator exports what `fyd` issued. `StateBoardAdminCapability` is that
# secret's sibling — same mint, same mode, same home, same delivery — so no distribution mechanism was
# invented, and inventing a SECOND one is what would have been the guess.
#
# WHAT MOUNTING FOUND, which no unit test had reached:
#   * `creatorMarkDone` CANNOT BE SERVED. The creation reducer adds `mark_done` to the creator's
#     `top_agent` actions and `TASK_BOARD_ROLE_ACTIONS` in the protocol grants `mark_done` to NO role,
#     so `TaskBoardMembershipSchema` rejects every board created with the flag — the CLI would refuse
#     the response it asked for. The route answers 501 naming the reason rather than creating a board
#     whose membership cannot be projected.
#   * A LONE MEMBERSHIP ROOT CANNOT RELINQUISH: the domain requires an accepted replacement root
#     first, so the invitation flow is the prerequisite for the exit, not an alternative to it.
#   * `{...world}` LOSES A CLASS-BASED WORLD'S METHODS. The mount binds each one by name; spreading
#     would have dropped `now`, `deliver` and `operatorCapabilityHash` onto the floor for any world
#     supplied as an instance rather than a literal.
#
# THREE ROUTES ARE STILL NOT SERVED, and none of them is a wiring:
#   * `POST /mark-done` and `POST /grants/revoke` — NO REDUCER EXISTS. `TaskBoardOperationKind` names
#     `mark-done.set` and `grant.revoke`, the audit events name them, the protocol declares both
#     request and response schemas, and nothing in `src/lib/task-boards` implements either. The only
#     revocations that exist are the ones relinquish and coordinator-replacement perform internally.
#     Mounting these means PORTING the domain.
#   * `POST /coordinator/replace` — the reducer exists and its authority model does not fit the wire.
#     `ReplaceCoordinatorCommand` takes an `administratorSessionId` checked by a
#     `TaskBoardAdministrator` predicate, so the domain expects a SESSION to hold administrator
#     authority; the command is authenticated by the OPERATOR, who is not a session and has no id for
#     that field or for the audit entry it becomes. Deciding who may take a coordinator's authority
#     away is a security decision, not a wiring one, so the mount passes a predicate that answers
#     `false` and serves no route that reaches it.
#
# ONE LIMITATION IN THE PRODUCT, stated because it is not obvious from the routes. A capability is
# delivered through the session's ENVIRONMENT STORE — the seam that already carries
# `FY_SESSION_BOARD_CAPABILITY` — and a pane reads its environment AT LAUNCH. So a session already
# running when its grant is issued picks `FY_BOARD_CAPABILITY` up on its next launch rather than
# immediately. The alternative, typing an export into a live pane, would write the secret into the
# transcript the agent later quotes back.
#
# `--board-access` AT SESSION START IS SERVED NOW, and the 501 it used to answer was wrong about the
# wire rather than merely unimplemented. The recorded reason said a start "would launch a pane holding
# a capability that authorizes nothing until a third party acts". A start hands the pane no capability
# at all: `TaskBoardChildGrantService.request` has no approval branch for ANY requester, coordinator
# included, so a pending intent is the only thing the domain can produce and refusing it meant
# `fy start --board-access` could not be run.
#
# The wire says which side owns the grant, and it took reading `IFyApiClient.start` rather than the
# route: it sends the parent's board capability on `x-fy-board-capability` with the START — the header
# has no other purpose on that surface — and its happy path returns the session without asking the
# board for anything, re-requesting the grant on exactly one path, after both POSTs died in transport.
# Those two facts only fit together if the daemon owns the grant and the recovery ask is a repair.
#
# WHAT MOUNTING IT FOUND: the client's repair could never have worked. It posted
# `/v1/task-board/child-grants/request` — SINGULAR — which no daemon serves, so the one call that
# exists to make a recovered `--board-access` start whole answered `unknown_route`. Both asks now

#
# The start also recorded `boardAccess: 'none'` on the session document for every session, whatever
# the caller asked for. A refused grant now retires its session with the board's own reason rather
# than leaving one that will never run: the grant is requested after the record exists and before the
# launch, which is the only window in which the board can see the target and a refusal costs no agent.
#
# THE LAST TWO LINES ARE GONE, AND THE REASON RECORDED FOR THEM WAS WRONG. They read "a board-scoped
# task mutation is `exact-worker-assignee`'s only possible caller, and the task routes resolve no board

# `TaskSubsystem.observe` turns a task's `assignee` into the session the live view reports, and it

#
# The recorded cost was real and it is what the fix is about: resolving a NAME means reading the

# PR #15 — add browser session control: THE HUMAN LOGIN WINDOW IS MOUNTED, nothing to list.
# The blocker recorded here for three units was accurate and it was a PORT, not a wiring: the host
# contract `BrowserLoginRuntime` was declared in adapters/browser/control/login-window.ts and nothing
# implemented it. `src/adapters/browser/control/login-runtime.ts` implements it now, and
# `src/lib/runtime/mounts/browser-login.ts` serves `GET`/`POST /v1/browser/login` — the route
# `fy browser login` and the PWA's login banner have both spoken since they were ported, against a
# daemon that answered `unknown_route`. `packages/pwa/src/lib/browser-login.ts` said so in its own
# header; that sentence is now history.
#
# THE DISPLAY IS OWNED, NOT INHERITED, which was the sharpening the second wiring unit recorded and it
# was right. `display()` is not "resolve $DISPLAY": the operator's own desktop is what $DISPLAY names,
# and this window's whole purpose is to publish a screen to whoever holds the VNC password. `XvfbDisplay`
# starts an Xvfb with `-displayfd`, which takes a free display and reports the number it took ONCE IT IS
# ACCEPTING CONNECTIONS — so one mechanism answers both "which display" and "is it up", and there is no
# window in which two daemons on one host choose the same number. It is created once and released by
# `cleanups`, because the runtime contract has no per-window release hook to hang it on.
#
# WHAT MOUNTING FOUND, which no unit test had reached:
#   * A `confirm` WITH NO WINDOW OPEN is classified `launch_failed` by the domain, not `bad_request`.
#     The mount passes the domain's split through rather than re-deciding it, so that answers 503 —
#     which is the honest reading: it is a statement about the window, not about the request.
#   * AN UNUSABLE DISPLAY ANNOUNCEMENT AND A DEAD Xvfb ARE DIFFERENT FAILURES, and the stream closing
#     wins the race against the exit being observed. Readiness is therefore a USABLE NUMBER rather than
#     merely an answer, so an Xvfb that died reports its exit status instead of "did not report a
#     display number" — the diagnostic an operator can act on.
#
# WHAT IS STILL NOT MOUNTED, and it is not a module on this list: per-session browser AUTOMATION.
# `/v1/sessions/:id/browser` is served as a stated 501 rather than a 404, matching `/v1/learning/run`,
# because `fy browser open` is a shipped command and a 404 is indistinguishable from version skew. Two
# things are genuinely absent, and neither is a wiring: the browser WORKER is a program this repository
# does not contain (`packages/daemon/bin/` ships `stt-worker.ts` and nothing else, and the only worker
# that exists is a test fixture), and nothing in production implements `BrowserViewerHost`. That pair is
# the same blocker the header records against `browserTransport`, and it belongs to the unit that ports
# the browser session runtime.

# PR #19 — port warden supervision: detection, verdicts, failover and provenance
# BLOCKED ON THE SUPERVISOR ITSELF. All four are policy for a sweep loop that does not exist: they
# decide which sessions get a warden, which account judges them, when a blessing suppresses an
# anomaly, and how a fleet attention view reads. Every one of them consumes durable warden state —
# assignments, strikes, blessings, the last sweep instant — and nothing writes any of it.
#
# `attention.ts` was investigated closely, because on paper the daemon holds all four of its other
# inputs: sessions from the index, boards from the attention ledgers it already serves, verdicts from
# the mounted WardenReportReader, and anomalies from `detectAnomalies`. It is the LAST of those that
# refuses. `detectAnomalies` takes a `hasLiveMonitor` per session, and this daemon mounts no monitor
# subsystem at all — `StorageSessionHealthInventory` is constructed with `monitors: false`. Every
# session in an actively-monitored status would therefore be detected as `dead_monitor`, and the
# fleet view would be a wall of one anomaly class that no warden exists to act on. Passing an empty
# anomaly list instead is worse: "nothing is wrong" is a claim nothing measured. The view lands with
# the monitor subsystem, not before it.
#

# mounted". It is not. `world.wardenReports` is a factory nothing ever calls, so `WardenReportReader`
# is REACHABLE — the composition root imports it — while the daemon serves no warden route at all.
# `/v1/warden/status`, `/v1/warden/run` and `/v1/warden/config` are all `unknown_route`, and status
