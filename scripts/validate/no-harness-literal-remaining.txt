# What still names a harness inside packages/plugins/runtimes/daemon, one row per file with the exact count. No file holds a harness LITERAL any more
# (a string that is exactly 'claude' or 'codex'); what is left is per-harness TABLES:
#
#   path::tables::N  a Record<HarnessKind, ...> (or Record<HarnessScope, ...>), a `satisfies`/`as` of one, or a mapped type
#                    `[x in HarnessKind]`. Their keys are identifiers, not quoted strings, so no literal row can count them
#                    (9 files, 14 tables; what each is is named below).
#
# Enforced by scripts/validate/no-harness-literal.sh. It is a NAMED, SHRINKING list, not an exemption: a new literal, a new table, a
# higher count or a row left behind for a file that is now clean all fail (exact both ways), and a row the base ref does not hold is
# refused (the ratchet). Never add a row to bless new code: put what the harness does in its plugin's kit
# (packages/plugins/runtimes/contract/harness-kit.ts) and look it up by the runtime's harness.
#
# The rows are CAPPED in scripts/validate/no-harness-literal.ts (PINNED): this list can only lose rows or lower a count.
#
# ── What PR 17b moved (it is gone from the rows below) ──────────────────────────────────────────────────────────────────────────────
#   17b-1: display names, scope words and labels (one table of words: `displayNameOf`, `shortNameOf`, `scopeWord`); install packages (the kits'
#     `install`); the settings file and format (`settingsFile`); the flags and `-c` keys a fixed layer owns (`carriedFlags`, `fixedConfigKeys`);
#     owned skill entries; the host folders and scanner home variables (`homeEnv`); the contract's HARNESS_WORD and CLI_WORD.
#   17b-2: Claude's comfort settings (the kit's `comfortSettings`, read where the built-in profiles are assembled); the sign-in model catalog of
#     each harness (the kit's `signInCatalog`, carried to the model assembly in `ModelCatalogSources.signIn`); where a profile's assets land
#     (HarnessAssetTable and HARNESS_ASSETS: the settings file, the instructions file and the `skills` folder come from what the kit already
#     says, and the kit's `assets` add only what is its own, so a Claude kit without it still lands every document where it always did; a kit
#     that names neither the settings file nor the instructions file lands them where KIT_FACTS says the harness always kept them); and
#     the mixed shape of a profile's scope, now a list of one layer per harness it reaches, in the order Runtimes lists them (no property each).
#     Which model ids belong to which harness left layering.ts for the table below (KIT_FACTS), because it must hold with a plugin OFF.
#
# ── What stays, and why ─────────────────────────────────────────────────────────────────────────────────────────────────────────────
# (B) Table rows that are kept on purpose:
#   lib/harness-kind.ts           KIT_FACTS (1): what must hold with a plugin OFF (a kit cannot say it): whether a harness keeps shared state,
#                                 whether its built-in profile layers comfort settings (a profile saved with them stays readable with the
#                                 plugin off), where its profile's settings and instructions land when its kit says nothing, which kit
#                                 members a runtime of it is refused without, and which model ids are its own (a harness's plugin
#                                 being off must never change what another harness's runtime does with a model set; kit-member-parity
#                                 pins it). Pinned to the kits by a drift test. And the mapped type KindOfKey (1), which with KEY_OF_KIND
#                                 is a plan exception
#   lib/models/catalog.ts         (3) per-harness data types, not behaviour: the halves a catalog reads, StarterModels and its builder
#
# (B') Table rows that are per-harness DATA, not behaviour (a stored or answered value per harness; they stay, but are counted so a new
#   per-harness table cannot hide among them):
#   lib/account/halves.ts (2: credentialHalves and its result), lib/account/import-plan.ts (2: the profile each harness got),
#   lib/account/import.ts (1: ImportRecord.profiles, a stored shape), lib/account/materialise.ts (1: harnessCommands),
#   lib/service/setup-service.ts (1: the names a person gave each harness's runtime), lib/service/catalog.ts (1: CatalogDeps.tools) and
#   lib/service/harness-facts.ts (1: harnessCommandsOf): the command each harness LOCATED to, a fact the caller fills
#
# (C) NOT counted by this gate, and named here instead (each is a value, not a harness-keyed type, so the gate cannot see it):
#   adapters/profile-components.ts       SOURCES: the Claude and Codex bindings (`ownedBy(ProfileClaudeSettingsSource)`, ...Codex..., and
#                                        the two hooks sources): the contract's own per-harness hook slots (`ProfileClaudeSettingsSource` ...), which
#                                        name the plugin that takes them, so they stay (a plan exception like KEY_OF_KIND)
#   lib/account/credentials.ts           SIGN_IN_FILES: Claude's and Codex's sign-in file names. It stays: `isSignInName` is the security
#                                        gate of document-link, fleet-disk, following-handle and host-harness-scan, and a sign-in file
#                                        must stay unreadable and unlinkable even when a plugin is OFF, which a kit cannot say
#
# (D) OUTSIDE this gate (it reads the daemon only): the contract side's own harness tables. They are the ONE table the app and the
#   daemon share, and the app holds no kits, so they stay (a plan exception like KEY_OF_KIND):
#   packages/plugins/runtimes/contract/display-name.ts   FERRETRY_SIGN_IN (a Ferretry-kept sign-in's words; adding them to the words table
#                                                        would change the words golden's fixture)
#   packages/plugins/runtimes/contract/harness-words.ts  the per-harness word table (catalog half, command word, host folder)
#
