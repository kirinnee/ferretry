# Skills inventory

One answer to "which skills exist here, and which one does this ferret see?" — the daemon side of the
"Tools & skills" page. The wire shapes are `packages/protocol/src/lib/skills-inventory.ts`.

## Routes

| Route                                          | Governance                   | Answers                                                             |
| ---------------------------------------------- | ---------------------------- | ------------------------------------------------------------------- |
| `GET /v1/skills`                               | operator, `fleet` / use      | every runtime home and every registered project                     |
| `GET /v1/sessions/:sessionId/skills/inventory` | operator (as `/skills`)      | exactly what that ferret sees                                       |
| `GET /v1/skills/file?path=…[&sessionId=…]`     | operator, `filesystem` / use | the SKILL.md text, for a path an inventory lists — exact match only |

`GET /v1/sessions/:sessionId/skills` (the composer's autocomplete list) is unchanged in shape. The Open route is
the **one exception** to "the daemon never returns SKILL.md contents": the file is the person's own, the path must
be one the inventory itself lists (a path that merely resolves to a listed one is refused), and the body is capped
at 256 KiB. `sessionId` widens the check to that session's listing, because a ferret's working directory need not be
a registered project.

## Scopes

- `ferretry` — a folder in a runtime home that is a link into `<FY_HOME>/fleet/assets/` (a Ferretry skill component).
- `user` — any other folder in the runtime home's `skills/`.
- `project` — `<root>/.claude/skills` for Claude, `<root>/.agents/skills` for Codex. `.codex/skills` inside a
  project is not read (Codex's own text names `$CODEX_HOME/skills` and `.agents/skills`).

A ferret reads its **runtime's home** (`<FY_HOME>/fleet/homes/<id>/skills`, found from the manifest by the wrapper
name in `session.config.agent`), not the daemon user's. A session that runs no fleet account falls back to the
daemon user's `~/.claude|.codex/skills`. The old behaviour read the daemon user's home for every ferret; that was a bug.

## Precedence (INFERRED)

Not verified against a running harness. Claude: a home skill overrides a project skill of the same name, so the
project entry carries `shadowedBy`. Codex: skills of the same name from both scopes are listed, so nothing is shadowed.

## Toggles

Every entry reports `toggle.supported: false` with a reason. The Codex binary (0.156) names a `skills.config`
selector by path or name, but `enabled` semantics were not verifiable here without running Codex, and
`config.toml` is regenerated by every apply, so a hand edit would be undone. Claude has no verified switch.
Ferretry components are switched by profile membership, which the profile editor already owns.

## Bounds

At most 200 skill folders per directory (`truncated` says when more existed), manifests over 256 KiB are skipped,
dot-entries (Codex's `.system`) are skipped, and a link whose target leaves the fleet directory (homes) or the
project root (projects) is dropped.
