## Mounting

The daemon-scoped Settings frame **is** on `main`
(`packages/pwa/src/features/settings/daemon-settings-frame.tsx`, mounted from
`settings-page.tsx`), and the daemon reads a client needs — accounts, config,
plan, usage, health — have all been mounted since PR #237/#252. The earlier
statement that the read endpoint still had to be added has expired.

The browser half has landed too. `packages/pwa/src/features/fleet/` carries the
wire client (`fleet-api.ts`), the pure read/projection model
(`fleet-change-model.ts`), the account and layer forms (`fleet-change-forms.tsx`),
the preview-and-result surface (`fleet-change-review.tsx`) and the composed tab
(`fleet-configuration-surface.tsx`), mounted from `App.tsx` as one
`daemonSettingsTabs` entry. So the answer to "where do I configure my fleet in
the UI" is now the daemon's Fleet tab, and `FleetSurface` is no longer
harness-only.

## Authority

Reads are admin-scoped and a paired device satisfies them. Composing a change is
also open to a device, because composing writes nothing at all.

Changing the host is not. A device applying a change must carry an approval that
the **host** minted for that one proposal: `POST
/v1/fleet/proposals/:proposalId/authorize` is `scope: 'host'`, so only the host's
own admin token may mint one, and `fy fleet authorize` is how a person gets it.
There is deliberately no loopback guard on the mint — unlike pairing, the code
confers strictly less than the admin bearer the caller already holds, so
requiring loopback would only break a legitimate remote admin. The code is
single-use, expires in two minutes, has a five-attempt budget bound to its own
proposal, never travels in a URL, and no read discloses it. Offering no code at
all costs no attempt, so a caller without one cannot burn the budget belonging to
the person who has one. Both policy numbers are declared in
`@ferretry/protocol`; the daemon parses its own mint through a schema that pins
them, while clients read them as plain integers so an older install still shows a
host the approval for a change its browser is already displaying.

The body-less admin `POST /v1/fleet/apply` is unchanged, and the existing device
refusals on it and on `PUT /v1/fleet/environment` are unchanged.

## GAPs that remain declared

- **Per-skill selection.** `skills` is one opaque directory in both originals and
  in Ferretry. There is nothing for a per-skill picker to bind to.
- **Home pruning.** The sweep is bounded to the wrapper directory, so removing an
  asset from the configuration leaves the copy already in an account home.
- **Settings key deletion.** `preserveExisting` folds the live file in as the base
  layer, so an edit merges over and a deletion does not remove a key on disk.
- **Comment-preserving YAML.** The configuration round-trips through the schema,
  so comments and anchors in a hand-written `config.yaml` do not survive the
  first edit made from a browser, and schema defaults are materialised.
- **Executable assets.** No slot exists for something like a status line.
- **Unsupported asset slots.** Claude has no `hooks` destination and Codex no
  `mcp` one; declaring either is refused at plan time rather than dropped.
- **Crash transactionality.** The rollback boundary covers a thrown error, not a
  killed task. A host that loses power mid-apply keeps its moved-aside evidence
  and its lock claim on disk under reserved prefixes; there is no journal-backed
  recovery and none is claimed.
- **Preparing a host has no undo.** Every file a scaffold writes is one that was
  absent, so taking them back could not be told apart from deleting files
  somebody else had just made. A run that stops part-way reports exactly what
  landed and where it stopped; running it again completes it.
- **Cross-invocation exclusion is a claim, not an abandonment recovery.** The
  apply lock never takes a claim over: reclaiming one needs an atomic
  compare-and-replace no filesystem offers, and getting it wrong permits the
  double apply the lock exists to prevent. An abandoned claim is named for a
  person to remove.
- **Reading an asset the editor will not touch.** A link, a binary, an over-limit
  file and one too deep in the tree are all listed with a reason and never
  returned. That is deliberate, not a shortfall — but it does mean the editor
  cannot repair such a file, only name it.
