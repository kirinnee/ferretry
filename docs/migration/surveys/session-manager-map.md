# Survey — `session-manager.ts` against the Ferretry daemon

`~/.config/home-manager/modules/kteam-ts/src/session-manager.ts` is 9,232 lines and 135 methods. It
is the core of kteam. Ferretry deliberately splits it across `packages/daemon/src/lib/**` under
subject names, so no filename comparison can tell us what is carried — this document is that
comparison, done symbol by symbol.

**How to read it.** Every row names a source symbol (with its line in the source at the time of the
audit), then either the Ferretry path that carries it or **GAP** with what is missing. A row marked
**GAP (unmounted)** means the module exists and passes its tests but no route or timer reaches it, so
the product does not have the capability — the distinction the reachability allowlist header makes.

**What was verified how.** The symbol inventory is complete: it was extracted mechanically from the
source, not sampled. The Ferretry side was established from the module tree, the mounted route table
(`lib/runtime/mounts/index.ts`), the protocol client's own call sites
(`packages/protocol/src/adapters/fy-api-client.ts`), and the reachability allowlist. Where a row says
PORTED, the named Ferretry module was opened; where it says GAP, the absence was established by
searching for the capability under every name it plausibly travels under, not by one grep. **Method
BODIES were not read line by line** — this map answers "is the capability carried", not "is it
carried identically". Rows where the shape is known to differ say so.

## The headline: the daemon serves 7 of the 8 session verbs the client speaks

`IFyApiClient` posts eight actions to `/v1/sessions/:id/<action>`. The daemon's route table answers
`unknown_route` to one of them.

| Client action | Daemon route                             | State                                                        |
| ------------- | ---------------------------------------- | ------------------------------------------------------------ |
| `stop`        | `POST /v1/sessions/:sessionId/stop`      | PORTED                                                       |
| `resume`      | `POST /v1/sessions/:sessionId/resume`    | PORTED                                                       |
| `migrate`     | `POST /v1/sessions/:sessionId/migrate`   | PORTED                                                       |
| `signal`      | `POST /v1/sessions/:sessionId/signal`    | **PORTED BY THIS UNIT**                                      |
| `send`        | `POST /v1/sessions/:sessionId/send`      | **PORTED BY THIS UNIT**                                      |
| `interrupt`   | `POST /v1/sessions/:sessionId/interrupt` | **PORTED BY THIS UNIT** — turn-stop only; bound abandon 501s |
| `answer`      | `POST /v1/sessions/:sessionId/answer`    | PORTED — see the recovery and reconciliation row below       |
| `rename`      | —                                        | **GAP**                                                      |

The GET surface is tracked row by row below. Operator `snapshot`, `logs`, `events`, and the
daemon-authoritative attach target are mounted; unserved surfaces such as per-session attachments
remain explicit GAPs in their own sections.

## F. The monitor loop — one responsibility of it now runs

A LOOP EXISTS. `lib/session/monitor` ticks the fleet on a timer armed in `bin/fyd.ts`, and carries
exactly one of `monitorLoop`'s responsibilities: `serviceWaiting` (C). It is per-daemon — the roster
is the session index of the storage that process opened — and it publishes `monitor.json` in the
state home on every tick, including a failed one, so a stopped loop is distinguishable from a fleet
with nothing parked.

Everything else below is still absent. The loop is shaped to take them: a tick is a plan over a
roster, so another responsibility is another planner, not another timer.

Two behaviours worth recording, both faithful to the source:

- **`abandoned_wreckage` can never fire from a sweep.** The sweep scans only
  `WARDEN_SCANNABLE_STATUSES`, which excludes `failed` and `stalled` — the very statuses wreckage is
  made of. kteam's `warden-detect.ts` has the identical list, so the class is dead there too. Left as
  found rather than silently widened.
- **An unwatched fleet is one fault, not N.** This daemon runs no monitors, so `hasLiveMonitor` is
  false everywhere and a raw sweep reports every live session as `dead_monitor`.
  `collapseUnsupervisedMonitors` restates them as a single fleet-keyed anomaly carrying every affected
  id. Passing `true` instead would report the fleet as watched AND switch on the sus classifiers over
  a liveness ledger nothing updates.

## What to take next, in the brief's own order of preference

1. ~~**`send` + `interrupt` + `answer`** (B)~~ — `send` and the turn-stop half of `interrupt` are
   done, and `endPeerWait` fires with them. `answer` is complete through durable idempotency,
   monitor reconciliation, bounded failure cancellation, diagnostic snapshotting, and release to
   prose. The remaining capability in this group is the public bound-abandon half of `interrupt`;
   it still needs the broader matcher family before it may target Escape at an arbitrary live form.
2. **Scratch GC** (L). Unbounded disk growth on the operator's machine, with the protocol shape
   already agreed.
3. ~~**The monitor loop** (F)~~ — partly taken. The TIMER exists and `serviceWaiting` rides it, so a
   declared wait now ends, and structured-question/answer evidence is reconciled on every tick.
   What is still GAP is every other planner that belongs on the same tick: the transcript watchers
   and their event handlers, `handleObservedInputs`, the stale-marker refusal, per-session quota polling,
   transient-retry firing and chat broadcast. Each is now an addition to a running loop rather than a
   loop of its own — take them one planner at a time.
4. ~~**The warden sweep runtime** (K)~~ — DONE. The sweep, its timer, the four `/v1/warden/*` routes
   and the durable state are mounted, and three of the four warden allowlist entries are gone. It was
   NOT "mostly wiring": the two honest decisions it forced — what an unwatched fleet means, and what
   a warden with no credential may be told to do — are recorded in K above. What remains behind it is
   provider-outage detection, migrate candidates and the needs-human suppression, all downstream of F.
