# PWA remaining-work map

Audited 2026-08-03 against `${KTEAM_SRC}/ui/src`, `packages/pwa/src`, merged
PWA PR bodies, and `docs/migration/HANDOFF.md` §14. This is the **43
TypeScript/TSX files** that a basename-only survey reported as missing (17,215
LOC). Tests and CSS are intentionally outside this executable-source count.

`PORTED-AS` means the capability is present, often under a feature-oriented
name. `PARTLY-PORTED` means most of a source file landed but a named capability
inside it did not, so the file may not be declared ported; the missing pieces
are itemised in `docs/migration/pwa-sessions-source-coverage.md` rather than
left as a footnote here. `DEFERRED` means the product deliberately chose not to
ship the capability in this increment; it is not an empty-state claim. The public
PWA must continue to obtain every daemon URL and credential through runtime
pairing, and any resulting store/cache/subscription must remain daemon scoped.

**This table has no row for first-run setup, and that is a fact about the source
rather than a gap in the survey.** `${KTEAM_SRC}/ui/src/pages` is Sessions,
NewSession, Chat, Settings, Warden, Learning and Analytics: there is no
onboarding, first-run or pairing surface to port, because that UI is served by the
local daemon to the same machine and has nothing to pair. Everything under
`packages/pwa/src/features/onboarding/` is therefore Ferretry-native, required by
the pairing split rather than carried across — so a unit looking for the source
symbol behind a setup screen should stop looking rather than keep searching.

## Result

The filename survey's **17,215 apparent LOC** now resolves to 34 PORTED-AS files
(12,163 LOC), 3 partly-ported files (3,354 LOC), 3 deferred browser-local STT
files (1,621 LOC), and 3 deliberate drops (77 LOC). No file remains blocked on
the app root: the production client now builds and renders without a daemon.
The counts overlap source-file boundaries only; a file that has a ported model
but an unported root component is correctly counted as deferred or partly
ported above.

The three deferred browser-local STT rows are unchanged in count but not in
meaning: dictation is no longer waiting on them. Browser `SpeechRecognition`
ships the capability (`ac6b8a35`), and what stays deferred is specifically
**on-device ONNX** recognition.

The app-root increment moved six rows to PORTED-AS (`main`, router, store,
notifications, notification delivery, and update detection), moved `App.tsx`
and `SessionChatPage.tsx` to explicit PARTLY-PORTED declarations, and converted
the three optional browser-local STT rows from a root blocker to DEFERRED.

A later increment then replaced the dictation engine outright, landing on
`main` as one squash merge (`ac6b8a35`): it moved recognition into the browser
and deleted the record-then-upload pipeline, so the eight PWA files that
existed only to feed a
daemon recogniser (`audio-capture.ts`, `pcm.ts`, `silence-segmenter.ts`,
`utterance.ts`, `daemon-engine.ts`, `capabilities.ts`, `capture-error.ts`,
`ort-precache.ts`) and the `src/worklets/` PCM16 worklet are gone rather than
ported. That is a **narrowing of the denominator**, not new porting debt.

Two earlier rows moved in opposite directions:

- `UnifiedBrowserSurface.tsx` (694 LOC) left GENUINELY-UNPORTED for PORTED-AS.
  `RemoteBrowserPane` now publishes the chrome/status/dispatcher contract the
  previous entry said it still needed, and `unified-browser-surface.tsx` drives
  it from one engine-agnostic toolbar.
- `SessionsListPage.tsx` (1,080 LOC) left PORTED-AS for PARTLY-PORTED. It gained
  a real connected page (`sessions-page.tsx`), but the audit that produced
  `pwa-sessions-source-coverage.md` found its inline `TranscriptResults` panel
  absent and two of its live feeds unconnected. That is a correction to an
  earlier over-claim, not a regression.

Two CSS apparent misses are also already carried: `components/attention-views.css`
→ `features/attention/attention-board.css`, and `components/task-views.css` →
the task feature's tokenized component styles / `task-dag-graph.css`. They are
not part of the 43 executable-file denominator.

## Next work, in order

The remaining work is no longer "port a missing file". It is finishing named
capabilities inside files that already exist — see
`docs/migration/pwa-sessions-source-coverage.md` for the itemised list.

1. The composer autocomplete popover — the cheapest and the most user-visible.
   Its source, `ui/src/components/ComposerAutocomplete.tsx`, is not in this
   survey's 43 files because the engine beneath it was ported separately; the
   engine is wired into `composer.tsx` and nothing renders its candidates, so
   Enter currently accepts an invisible row instead of sending. One component.
2. Fleet-event reconciliation — the daemon already mounts `/v1/events`. What is
   missing is browser ticket issuance plus a reconcile path into
   `fleet-store.ts`'s per-daemon slice, which today hydrates once. This is what
   makes the sessions dashboard live rather than a snapshot.
3. The complete session workspace — compose the existing transcript, composer,
   files/tasks/browser side panes and event/history feeds behind the now-mounted
   daemon/session route. The current fallback is intentionally honest and
   collision-safe, but it is not the migrated chat product.
4. The transcript-search route — daemon work first (`IFyApiClient` has no
   search), then the `TranscriptResults` panel that `SessionsListPage.tsx`
   rendered inline.
5. The warden-verdict feed — a protocol schema first; the renderer already
   exists and the dashboard is passed an honest empty list until then.
6. Transcript render-hold consumption — `use-live-clock.ts` exposes the gate and
   only the live clock reads it; kteam's measured fix was the transcript itself
   holding still. Belongs to the transcript unit.
7. Optional **device-local** STT — only if product chooses the ~640 MB model and
   ~25 MB WASM trade-off. Dictation itself is complete through the browser's
   `SpeechRecognition` API; the open question is recognition that provably never
   leaves the device, which the browser engine does not promise (some vendors
   send the audio to their own hosted speech service). The named amplitude-meter
   GAP belongs with it: `components/input-waveform.tsx` is kept with its
   fidelity rules and tests, and Web Speech exposes no analyser stream to feed
   it, so a real meter only exists for a host that owns its own audio graph.
