# v4 home formats — what the v4 → v5 converter reads

Every file Ferretry **4.291.x** writes under `FY_HOME` (default `~/.ferretry`), who writes it, how it is parsed, and
which v5 file (§9.2 of [`docs/design/redesign.md`](../design/redesign.md)) it becomes. It is the input contract of the
one-time converter at `migration/v4-to-v5/` and of the runbook [`v4-to-v5-prompt.md`](v4-to-v5-prompt.md).

- **Source**: today's code at `bb89d054d` (4.291.5), read from the `rebuild-ref` worktree. **No real home was
  opened** to write this page. Writers and schemas are cited as `file:line` in that tree (`D` = `packages/daemon/src`,
  `F` = `packages/fleet/src`, `C` = `packages/cli/src`, `P` = `packages/protocol/src`).
- **Product rule**: nothing here is read by v5. The product keeps zero v4 readers (A452); the converter keeps its own
  v4 parsers, and both are deleted once every machine is on v5.
- **Secret rule**: rows marked **sealed/secret** are moved byte for byte (`copyFile` + mode + times, the same as
  `cp --preserve`) and are **never opened, decrypted, printed or logged**, by the tool or by the agent running the
  prompt. Their formats below are described from code, never from a file.
- Unless a row says otherwise, every v4 JSON/JSONL file is written atomically (temp in `state/tmp`, rename), mode
  `0600` in `0700` folders (`D/adapters/filesystem/state-file-system.ts:350-402`). Most v4 documents carry **no
  format field**; v5 puts `"format": 1` first, so the converter adds it.

## 1. What the converter must not get wrong

1. **The daemon identity must not change.** `state/daemon-identity.json` (`{schemaVersion:1, privateKeyPem}`, an
   Ed25519 key) is the `daemonId` every paired browser pins. `devices.json`, `unlocks.json`, catalogs'
   `member-unlocks.json` and `links.json` (`publisher`), board cards (`machineId`), the attachments folder
   (`state/attachments/<daemonId>/…`) and `terminal-pane.json` all name it. A new identity means every device pairs
   again, every unlock is lost and every catalog link ends with `identity-changed`.
2. **The vault does not bind to a path.** AES-256-GCM, a 12-byte random IV per value, key = base64 of 32 random bytes
   in `state/secrets.key` (no KDF, no keychain), **AAD = the value's name only** (`catalog-link:<linkId>` for link
   keys). Nothing binds the ciphertext to a path, file name, home or daemon id, so `secrets.key` plus the four sealed
   documents that share it (`secrets.json`, `login-secrets.json`, `mcp-oauth-secrets.json`,
   `catalogs/link-keys.json`) open after a byte-for-byte move, **provided the v5 Vault keeps the AAD rule and the
   `cipher: "AES-256-GCM"` check** (spine D16). Merging them into one document would be a re-seal: not allowed.
3. **`push-vapid.json` and `push.json` move together** (every subscription was made against that VAPID key), or
   every phone silently stops getting pushes.
4. **The harness folders are keyed by runtime, not by ferret.** `fleet/homes/<runtime uuid>/` is a runtime's
   `CLAUDE_CONFIG_DIR` / `CODEX_HOME`; its conversation folders are **absolute symlinks** into the shared pool
   `fleet/shared/<claude|codex>/`, which holds **the transcripts resume needs** (Claude
   `projects/<encoded cwd>/<conversation>.jsonl`, Codex `sessions/YYYY/MM/DD/rollout-*.jsonl`, Codex `sqlite/`). The
   pool moves whole and verbatim; links are re-made.
5. **The resume id** is `state/sessions/<sid>/config.json` → `transcript.harnessSessionId` (with `transcript.home`
   and `transcript.file`, both absolute paths). `identity: "undiscovered"` means the ferret has no resumable
   conversation.
6. **Absolute paths of the old home are baked in**: session `config.json` (`transcript.home`, `transcript.file`,
   `command[0]` = the wrapper `fleet/bin/<runtime>`, `cwd`), `fleet/manifest.json`, wrappers, harness-home links,
   warden `state.json` (`investigations[].reportPath`, `sweepCoverage.reportPath`), `catalog-installs.json` (project
   paths). Generated ones are regenerated; data ones are rewritten.
7. **Ids are joined across files**: the session id `<sid>` (folder name = `config.id`) is referenced by cards,
   agenda ledgers, drafts, pins, archive, callsigns, worktrees, learning, warden, renders and attachments — keep it
   unchanged. Runtime **names** join sessions (`config.agent`) to `config/runtimes/<name>.yaml`; runtime **uuids**
   (`fleet/ids.json`) join `config/routing.json` and usage rows. Login ids join `config/logins/<id>.yaml`,
   `fleet/credentials/<id>/` and budgets. Agenda item ids `A<n>` are unique **per session** only.
8. **A ferret's credential**: the plaintext is in `state/sessions/<sid>/environment.json` (secret) and in the live
   pane's environment; its SHA-256 is `config.json` `sessionCapabilityHash`. v4 stores no admin/warden token hash:
   `api-token` and `api-warden-token` are plaintext files at the home root.
9. **The tmux server's socket is `<FY_HOME>/tmux.sock`** (home root, not `state/`). The tmux session of a ferret is
   `config.tmuxSession`; its pane is `terminal-pane.json`, with the fields
   `{daemonId, sessionId, tmuxSession, paneId, pid, processStartTicks}`.
10. **A v4 that did not stop cleanly** leaves intents behind (`agenda-*.pending.json`, a `fleet/.fy-fleet-apply.lock/`,
    a `fleet/shared/<harness>/.migration-journal`). The converter refuses such a home; restart and stop v4 cleanly.

### 0. The five things the converter must not get wrong

1. **The vault does not bind to a path.** See §2. AAD is the secret's name (or `catalog-link:<linkId>`), never a path, file
   name, home or daemon id. A byte-for-byte move to a new path/home opens, as long as `secrets.key` moves with
   `secrets.json` and the v5 reader keeps the same AAD rules.
2. **The daemon identity is the one thing that must not change.** `state/daemon-identity.json` holds the Ed25519 private
   key (PKCS#8 PEM). Its SHA-256 fingerprint is the `daemonId` (`fy_daemon_…`). It is checked or used by these places:
   - `devices.json.daemonId`. A mismatch with the identity makes pairing refuse to open: `throw new Error('device grants belong to a different daemon identity')` at `D/adapters/pairing/state-pairing-repository.ts:147,155`.
   - `unlocks.json.daemonId`, and `catalogs/member-unlocks.json.daemonId`. A mismatch is read as "holds nothing", so every device would unlock again (`D/adapters/step-up/state-unlock-ledger.ts:73`).
   - `catalogs/links.json` `links[].publisher`, and the link-store Worker, which recognises the owner by daemon id. A change ends links with reason `identity-changed`.
   - catalog signatures (manifest and list), and every paired browser's pinned fingerprint.
3. **`push-vapid.json` and `push.json` are a pair.** Every stored subscription was made against the VAPID public key
   derived from `push-vapid.json`. Move both or neither, or every phone silently stops getting pushes.
4. **Admin and warden tokens are plaintext files at the `FY_HOME` root, not under `state/`** (`api-token`,
   `api-warden-token`). v4 stores no token hash. Nothing in v4 stores a device token or its digest.
5. **Absolute project paths live inside `state/catalog-installs.json`** (`root`, `folder`, `key`, `target.projectRoot`).
   They are not path-bound crypto, but they go stale if the project folders move. See §4.

### 2. Secrets vault, sealing format, and every holder of `secrets.key`

#### Exact sealing (all from code)

- **Key**: `state/secrets.key` (`SECRETS_KEY`, `D/adapters/secrets/file-secret-document-store.ts:25`; path
  `join(paths.state,'secrets.key')` `:65`). Content is **base64 of exactly 32 random bytes + `\n`**
  (`FileSecretKey`, `D/adapters/secrets/webcrypto-secret-cipher.ts:53-85`; minted with `randomBytes(32)` on the first write; 0600).
  A present but not-32-byte file raises `undecipherable`. It is read raw: **no KDF, no passphrase, no OS keychain**, and the key is
  imported straight as AES-GCM `raw`. A vault with entries and no key file raises `key_missing` (`file-secret-document-store.ts:80`).
- **Cipher**: AES-256-GCM via WebCrypto (`SECRET_CIPHER_ALGORITHM='AES-256-GCM'`, `webcrypto-secret-cipher.ts:6`), 96-bit random IV per seal.
  `ciphertext` = base64 of ciphertext with the 16-byte tag appended (WebCrypto default); `iv` = base64 of the 12 bytes.
- **AAD** = `utf8(<sealed name>)` and **nothing else** (`webcrypto-secret-cipher.ts:114-117,154-158`). Moving an entry under another name fails the open.
- **Nothing binds the ciphertext to**: an absolute path, the file name, the home path, the host name, or the daemon identity.
  The only locational coupling is that the key is read from `secrets.key` **in the same `state/` directory as the document**
  (code derives both from `paths.state`). The v5 reader must also check the document's `cipher` string equals `AES-256-GCM`
  exactly, or v4 raises `unreadable` (`D/lib/secrets/vault.ts:38-45`).
  **Conclusion: a byte-for-byte move of `secrets.json` + `secrets.key` (and the other sealed documents) to a new path or home opens fine.**
  The failure modes are only: the key not moved, a changed AAD rule, or an edited entry name.

#### Board cross-file references the converter must keep consistent

- `card.owner`, `card.assignee`, every `history[].actor.sessionId`, `createdBy.sessionId` → **session ids** (`state/sessions/<sid>/`). Sessions on open cards are _retained_ from archiving (`fyd.ts:2081-2087`); if a v5 session id is renamed these must be rewritten.
- `card.machineId` (and any `TaskRef.machineId`, `dependsOn[].task.machineId`, `parent.machineId`) = the **daemon id** = SHA-256 fingerprint of the identity key in `state/daemon-identity.json` (`fyd.ts:8545` `attachmentDaemonId = state.daemonId`; refs with a foreign machineId are treated as remote at `fyd.ts:10061, 12347`). **Carry the identity key byte-for-byte or every card's `machineId` goes stale.**
- `card.projectId` → `state/projects.json[].id` or `unfiled`; `card.laneId` → `board/lanes/<projectId>.json` lane ids (`LaneIdSchema`, `board-lanes.ts:63`).
- `card.parent`, `card.dependsOn[].task` → other card ids (may be on another machine's board: `{machineId,id}`).
- `card.approval = {sessionId, id}` → an **agenda item** `A<n>` in that session's `agenda.json` (`board.ts:112`).
- `card.legacyRef = "<sid>:<T-id>"` → retired `tasks.json` (kept for provenance only).
- Board attachments (`BoardAttachment {id: att_<sha256>}`) point into the per-session attachment store (`adapters/board/board-attachments.ts`), not this area.

### 6. Cross-part cautions for the converter (area C)

- **Identity key coupling:** card/ref `machineId` and notification/attachment keys derive from the daemon id = fingerprint of `state/daemon-identity.json`. Move that file byte-for-byte (sealed; another area).
- **Session id coupling:** cards (`owner`, `assignee`, history actors), agenda ledgers (`sessionId` must equal dir name), learning observations, warden state, notifications all hold session ids — keep session ids stable or rewrite everywhere.
- **Project UUID coupling:** `state/projects.json[].id` ↔ `board/lanes/<id>.json`, `card.projectId`, session `projectId`, `account-defaults.yaml.projects`.
- **Runtime uuid → name:** `routing.json accounts[].accountId` (uuid) vs v5 runtime names; see Part 1 (`fleet/ids.json`).
- **Absolute paths:** wrappers, `fleet/manifest.json`, harness-home symlinks and several session docs embed the old FY_HOME path (Part 0/§4); warden state carries `reportPath` absolutes (Part A §3).
- **Quiesce first:** transient intents (`agenda-versions.pending.json`, `agenda-changes.pending.json`, `fleet/.fy-fleet-apply.lock/`, `state/tmp/*.tmp`, `daemon.lock`) mean the v4 daemon was not cleanly stopped; the converter should refuse or run v4 once to settle.
- **Machine-agenda/`agenda-history` cursor:** carry `agenda.json` and `agenda-history.jsonl` together byte-for-byte.
- **Not persisted at all in v4 (no source file):** board GitHub watcher state, MCP inventory, skills inventory, work-search index, stt/local-models/harness-update/tidy state (see Part B §1d).
