[own] GAP(snapshot-wrap): the screen masker (maskedScreen, one file kept byte-for-byte the same in Ferrets' daemon/lib/session/snapshot/screen-mask.ts and Terminals' daemon/lib/tmux/screen-mask.ts, used by last-snapshot.txt and by the live Runner.look) stars a value tmux wrapped at the pane edge, or the harness UI broke inside its indent, marker or box border, but it cannot see the end of a value whose start has scrolled off the top of the screen (RedactionScope matches whole values only, so a suffix needs a kernel contract change or a capture of the rows above the screen, which only a real-tmux test can prove), a break whose continuation starts or ends with a character the UI draws that its gutter set does not name, a value in a table column that is not the last one (the next column's border and cells stand between its pieces, so no reading rebuilds it), or a value broken over three or more rows whose breaks meet in different ways (one at a trimmed space, one not); and a screen over 262,144 characters, which the masker REFUSES whole (it is never cut before masking and never passed on unmasked, as a masked screen is read several times over and 500 dense values on a 200 by 2000 screen took about 0.8 s of the main thread here): that pane's look answers no evidence, so its turn is not decided from the pane, and a stop keeps no last screen for it, for as long as the screen is that large (a real pane is far under: 400 columns by 200 rows is 80,000 characters; today's daemon had no masker of this kind to compare it with). The cap bounds the size of a screen, NOT the time to mask it: the cost is the screen's size times the Vault's size, and more again when its values are on the screen: a 400×200 pane takes about 4–38 ms with 10–100 Vault values and about 0.57 s with 2,000 dense values, so a look can pass the ~5 ms slice on an ordinary pane too, and a screen just under the cap measured with the real VaultRedaction took about 0.5 s of the main thread with 500 dense values and 1.8 s with 2000 (about 100 to 350 times ruling #44's ~5 ms slice); a screen over 16,384 characters is masked in slices (the masker yields between its up-to-six readings, before the per-row check and before the final text pass), so the longest slice is one reading, not the whole masking; what is left: one reading is still one synchronous slice, which on a dense screen near the cap can still pass the ~5 ms, and masking off the main thread or in chunks cut on value-safe boundaries needs a kernel redaction change (owner: gustavo); the cap was kept at 262,144 because bringing a dense look down toward 5 ms would take a cap of a few thousand characters, which WOULD refuse ordinary panes, and today's daemon had no masker to keep parity with
